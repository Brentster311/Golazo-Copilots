# GCP-0014: Design Doc - Project Owner Consent Required for Gate Bypass

## Summary

Enhance `gcp_consent` to clearly communicate that consent must come from the **Project Owner (human)**, not the AI assistant. The rationale is already required and stored, but the tool description and output messaging don't make the PO requirement clear. Additionally, `gcp_status` should display recorded deviations.

---

## Problem Statement

Currently, the AI assistant can invoke `gcp_consent` with a reason it generates itself, rather than requiring the Project Owner to provide the rationale. This undermines the gate bypass audit trail because:

1. The "reason" may be AI-generated, not PO-provided
2. There's no explicit prompt reminding the assistant to ask the PO first
3. `gcp_status` doesn't show recorded deviations, making them invisible

---

## Business Case

**Why now**: Gate bypasses without proper PO consent undermine workflow integrity.

**Impact**: Ensures audit trail reflects genuine PO decisions.

**KPIs**:
- 100% of deviations have human-provided rationale
- Deviations visible in status output

---

## Stakeholders

- Project Owner (primary user)
- AI Assistant (Copilot - consumer of tool)
- Auditors (consumers of deviation logs)

---

## Functional Requirements

1. **Tool Description Update**: `gcp_consent` description must state:
   > "Record Project Owner consent for bypassing workflow gates. The rationale MUST be provided by the Project Owner (human), not generated by the assistant."

2. **Response Messaging**: Output should remind:
   > "Consent recorded from Project Owner."

3. **Status Deviation Display**: `gcp_status` must include a `deviations` section showing:
   - Deviation ID
   - Action type
   - Rationale text
   - Timestamp
   - Whether consumed

---

## Non-Functional Requirements

- No change to state.json schema (Deviation already stores `reason`)
- Backward compatible (existing deviations remain valid)

---

## Proposed Approach

### 1. Update `gcp_consent` tool description in `server.py`

Update the `@mcp.tool()` decorator or description to emphasize PO requirement.

### 2. Update `gcp_consent` return message

Change:
```python
"message": f"Consent recorded. You may now use force=True for {action}."
```
To:
```python
"message": f"Consent recorded from Project Owner. You may now use force=True for {action}."
```

### 3. Add deviations to `gcp_status` output

In `gcp_status.py`, include:
```python
"deviations": [
    {
        "id": d.id,
        "action": d.action,
        "reason": d.reason,
        "timestamp": d.timestamp.isoformat(),
        "consumed": d.consumed,
    }
    for d in state.deviations
]
```

### 4. Update server.py formatted output for status

Add a deviations section to the formatted status:
```
**Deviations:**
- dev-001: skip_role - "Work already implemented" (consumed)
```

## Alternatives Considered

| Alternative | Reason Rejected |
|-------------|-----------------|
| Interactive confirmation prompt | MCP tools don't support interactive prompts |
| Separate `po_consent` tool | Unnecessary complexity - same tool, clearer messaging |
| Require specific format for rationale | Too rigid, free text is sufficient |

---

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| AI still generates rationale | Tool description explicitly says "MUST be provided by PO" |
| Existing tests break | Update test expectations for new message format |
